一作品概述

「漫途」是一款面向自由行人群的微信小程序。它把旅行前最耗神的三个动作—— 读攻略、定行程、找人问——收进一个入口：用户说出想去的地方和偏好， AI 给出可执行的行程与讲解，社区里的真实攻略再补上「别人踩过的坑」。

1.1 一句话定位

一个用 AI 降低旅行决策成本、用社区沉淀真实经验的文旅攻略共创平台。

1.2 作品简介

小程序以原生技术栈开发，共 22 个页面、5 个一级页签（首页 / 社区 / 攻略 / 目的地 / 我的）， 内置 17 条结构化攻略与 17 个目的地资料。AI 能力由本地部署的 DeepSeek-R1:7B（Ollama）提供，通过零依赖 Node 服务桥接，覆盖三类场景： 攻略的多主题讲解（历史 / 美食 / 摄影 / 亲子等视角切换）、 自然语言转结构化行程、以及按表单生成攻略初稿。 当模型或服务不可用时，小程序自动降级为本地模板与内置数据，功能不中断——这是为参赛演示环境专门设计的可靠性方案。

1.3 与常见方案的差异

对比项常见旅游 App / 小程序漫途的做法
内容来源平台编辑或爬取的聚合内容，千篇一律用户共创 + 结构化模板，发布即进入可检索的攻略库
AI 使用方式一个空白输入框，让用户自己「会提问」表单化的结构化输入，把提示词工程藏在界面背后
攻略呈现长文，读完才知道是否适合自己同一篇攻略可按主题切换讲解视角，按需取用
可靠性断网或服务异常时直接空白AI 可缺席：本地缓存兜底，主流程始终可走通

1.4 完成度

作品已完成从浏览、收藏、登录、足迹到创作、发布、AI 生成、后台管理的完整闭环， 前后端均可独立运行，代码已整理为公开仓库并通过静态检查与功能用例验证。

二背景与用户痛点

2.1 需求背景

自由行已成为主流出行方式，但信息供给与决策效率严重不匹配：攻略平台内容过载， 同一目的地的笔记动辄上千篇，用户需要花大量时间筛选；而行程规划仍依赖手工拼装， 交通、住宿、景点、餐厅之间的时序约束很少有人能一次排对。

大模型的成熟让「把自然语言需求直接变成可执行行程」成为可能，但通用聊天工具存在三个落地障碍： 输出不可控、结果不可复用、离线不可用。文旅场景恰恰要求可控、可保存、可分享。

2.2 目标用户

用户类型典型特征核心诉求
首次自由行者没有目的地经验，怕踩坑要一份能照着走的行程，而不是一堆笔记
深度体验者对历史、美食、摄影有明确偏好同一地点想要不同视角的讲解
经验分享者走过的地方多，愿意输出发布门槛低，发出去有人看、能被检索

2.3 核心痛点

  1. 筛选成本高：攻略数量多但结构不统一，读十篇才能拼出一条路线。
  2. 规划门槛高：行程要兼顾时间、距离、体力与预算，普通人缺少方法论。
  3. 内容同质化：AI 生成内容若不加以约束，容易产出「看起来都对、实际去不了」的行程。
  4. 工具不可靠：旅行途中网络不稳定，依赖云端 AI 的工具一旦断连就失去价值。

2.4 需求边界

作品聚焦「行前决策」这一环，不做订票、支付、导航等交易与履约能力； 内容以结构化攻略为主体，AI 承担讲解与初稿生成，最终由用户确认后发布。

3.1 功能清单

模块能力实现要点

3.2 技术架构

采用「轻前端 + 薄后端 + 本地模型」三层结构，全部组件零第三方依赖：

  • 表现层：原生微信小程序，22 个页面，自定义导航栏组件，无 UI 框架。
  • 服务层：Node.js 原生 http 模块实现的单文件服务（171 行）， 提供 /api/chat 模型桥接与 /api/guides 攻略 CRUD，数据落 data.json。
  • 模型层：Ollama 本地推理 deepseek-r1:7b，通过 HTTP 调用，非流式返回。
  • 兜底层：小程序本地 Storage 保存用户资料、收藏、足迹与攻略缓存，服务不可用时接管全部读写。

四AI 技术方案

4.1 模型选型

选择本地部署的 DeepSeek-R1:7B，通过 Ollama 提供 HTTP 接口。 理由有三：中文语义与常识推理表现稳定；7B 量化后可在普通笔记本上运行，演示不依赖外网； 本地推理意味着用户输入不出本机，隐私风险最低。

4.2 三类 AI 能力

能力输入输出与约束
主题式攻略讲解攻略正文 + 主题（历史/美食/摄影/亲子/省钱）同一内容多视角重述，禁止编造景区事实，长度受控
行程生成目的地、天数、预算、同行人、偏好按天分段，含时间、地点、理由，附预算估算
攻略初稿生成结构化表单（地点、天数、亮点、贴士）输出可编辑草稿，用户确认后才进入社区

4.3 提示词与输出处理

  • 结构化输入替代自由提问：用户只填表单，提示词由程序拼装，降低「不会提问」造成的质量波动。
  • 思维链过滤：R1 系列会输出 <think> 段落，服务端统一剥离后再回传，前端只呈现结论。
  • 多字段兼容解析：兼容 reply / response / answer / text / message 及嵌套结构， 避免模型或网关字段变化导致解析失败。
  • 分级超时：端侧等待 120 秒、服务端转发 180 秒，超时即降级，不无限挂起。

4.4 可靠性设计：AI 可以缺席

设计原则：AI 是增强项，不是必需项。任一环节失败都不得阻塞用户主流程。
  1. 写操作先落本地 Storage，成功后再异步同步后台；同步失败仅提示「已存本地」。
  2. 模型不可用时，攻略讲解回退到内置文案，行程生成回退到模板化建议。
  3. 后台服务离线时，社区与后台管理页显示离线状态，读写全部转本地，功能仍可用。

4.5 成本与合规

本地推理无按次调用成本，适合赛事演示与小规模验证；用户输入不出本机， 规避了第三方模型服务的数据外流问题。若后续对外发布，将改造为「云端模型 + 内容安全审核」的组合方案。

五创新点说明

01
可切换主题的攻略讲解 同一篇攻略不再只有一种读法。用户按「历史 / 美食 / 摄影 / 亲子 / 省钱」切换视角， 由 AI 重述内容重点。解决了攻略「读完了才发现不是我要的」这一筛选成本问题， 也让已有内容被反复利用，而不是不断重复生产。
02
结构化输入替代自由提示词 把「提示词工程」从用户侧移到程序侧：用户只见表单，不见 Prompt。 输入维度固定（目的地、天数、预算、同行人、偏好），输出因此稳定可比， 既降低使用门槛，也避免模型自由发挥导致的行程不可执行。
03
可信度分层 平台明确区分三类内容：内置结构化攻略（人工核校）、用户共创攻略（真实经历）、 AI 生成初稿（标注来源、需人工确认后发布）。三层内容不与混同， 用户一眼能判断「这条信息该信到什么程度」。
04
AI 可缺席的可靠性设计 与多数「AI 挂了就白屏」的产品不同，本作品把降级当作一等公民： 先写本地、再同步后台，模型不可用则回退模板。 在网络不稳的旅行场景与离线演示环境下，功能依然完整可用。
05
端云协同的本地兜底 小程序端承担全部读写兜底，Node 服务只做模型桥接与多端同步， 职责边界清晰、部署成本极低（单文件服务、零依赖、一键启动）， 适合校园团队长期维护，也便于迁移到云托管。
创新点小结：不是把大模型塞进小程序，而是重新设计了「人—AI—内容」的分工： AI 负责重述与初稿，人负责确认与经验，系统负责在任何一环失效时仍然可用。

七应用价值与后续规划

7.1 应用价值

  • 对用户：把「查十篇攻略 + 手工排行程」压缩为一次表单填写，决策时间显著下降。
  • 对内容生态：结构化模板降低发布门槛，AI 初稿让「想分享但不会写」的人也能产出内容。
  • 对文旅行业：沉淀的结构化攻略可作为目的地运营的内容底座，支持按主题二次分发。
  • 对教学：完整呈现了「小程序 + 轻服务 + 本地大模型 + 降级设计」的工程化落地路径，可复用为课程案例。
